## 1. What the Ecosystem Is

A **cluster ecosystem** is the higher-order structure that binds a cluster's **purpose**, **tools**, **progression**, and **success definition** into one coherent model. It answers: *"What does success look like for this cluster, and what system gets members there?"*

Every cluster has an ecosystem, whether implicit or explicit. Before this document, ecosystems were implicit — inferred from tone, features, and tags. This document makes them **explicit, measurable, and evolvable**.

### 1.1 Ecosystem vs. Cluster Spec

| | **Cluster Spec** (`cluster_genesis_spec`) | **Cluster Ecosystem** (`cluster_ecosystem_spec`) |
|---|---|---|
| **Answers** | "What is this cluster?" | "What does success look like, and how do we get there?" |
| **Contains** | Tags, stakeholders, vibe, features, rules | Success dimensions, progression stages, tool requirements, introspection targets |
| **Generated by** | Genesis Engine (Day 0) | Genesis Engine (Day 0), evolved by Observer |
| **Owned by** | Admin (with Genesis validation) | Admin + Observer + (optionally) members |
| **Changes** | Rarely — only if spec drift is severe | Regularly — every 14–30 days via Observer review |

### 1.2 Where the Ecosystem Sits

```
FOUNDER INTENT
      ↓
GENESIS ENGINE → generates cluster_spec + ecosystem_spec (co-generated)
      ↓
INITIAL ADMIN REVIEW → admin reviews ecosystem spec, approves or requests edits
  └─ Status: pending_admin_review → active (after approval)
      ↓
CLUSTER ECOSYSTEM (this document)
  ├─ success_model (what does success look like?)
  ├─ progression_model (how do members advance?)
  ├─ tool_requirements (what tools serve which success dimensions?)
  ├─ introspection_targets (what does Observer measure?)
  └─ ecosystem_phase (Seed | Sprout | Canopy)
      ↓
CIMs — measure ecosystem health per dimension
      ↓
OBSERVER ↔ ECOSYSTEM (bidirectional loop)
  ├─ Ecosystem tells Observer: "Watch these dimensions, these thresholds"
  ├─ Observer tells Ecosystem: "This dimension is off-track, this need is latent"
  └─ Admin edits ecosystem → Observer remeasures → loop continues
      ↓
GENESIS RE-EVAL GATE (NEW — §10 of CLUSTER_GENESIS_ENGINE.md)
  ├─ Scheduled: quarterly baseline re-evaluation of ecosystem_spec
  ├─ Emergency: triggered by persistent drift (≥3 cycles), multi-dimensional
  │   mismatch, founder-intent floor breach, or post-change reversal cascade
  ├─ IF paradigm shift confidence < threshold:
  │     → Pass through to Governor (operational cycle continues)
  └─ IF paradigm shift confidence ≥ threshold:
        → Document + Timestamp
        → Evaluate adverse impact (low / medium / high)
        → IF high adverse impact: Admin approval required (hard pivot)
        → IF approved: Hard pivot of ecosystem_type, success_model, progression_model
        → Explicit 6-step member communication (autism-safe protocol)
        → History preserved; rollback available
      ↓
EVOLUTION GOVERNOR — routes proposals: auto-approve | admin review | member deliberation
      ↓
SAGE / CLIO — execute: teach current stage, nudge to next, celebrate mastery

**Genesis Re-Eval is initialization-grade inference applied operationally.**
It is NOT part of the continuous loop — it is a controlled escalation that
intercepts the loop and asks: "Is the framework itself still valid?"
```

### 1.3 Ecosystem Types and Social Layer Defaults

The ecosystem's success dimensions and progression model vary by `ecosystem_type`. Critically, **social interaction is not assumed** — it is an overlay that the guardian elects.

| Ecosystem Type | Primary Beneficiary | Default Social Layer | Example |
|---------------|---------------------|----------------------|---------|
| `learning_management` | Minor (13–17) | **Disabled** — guardian gets dashboard, minor gets learning surface | "Quran Learning for Teens" — minor learns; guardian sees progress dashboard |
| `social_learning` | Minors collectively | **Enabled** — peer discussion, shared resources | "Teen Study Circle" — minors study together, discuss, share insights |
| `peer_support` | Minors collectively | **Enabled** — mutual aid, shared experience | "New Muslim Teens Circle" — minors support each other through shared journey |
| `career_reintegration` | Minor (13–17) | **Disabled** by default — can opt into peer networking | "Teen Career Prep" — minor gets coaching; guardian sees summary; optional peer group |
| `community_health` | Minors collectively | **Enabled** — group accountability, shared goals | "Teen Prayer Circle" — collective habit tracking with guardian visibility |

#### 1.3.1 Canonical archetype defaults (advisory)

To avoid overfitting the architecture to a rigid grid of `purpose_type × ecosystem_type`, Aggilo maintains a **small library of canonical archetypes** with recommended defaults. These are **starting points**, not hard locks; Observer and Evolution Governor are expected to tune away from them when lived behaviour diverges.

Examples:

| Archetype | Typical Ecosystem Type | Suggested Social Layer | Suggested Progression Model | Experience promise (internal) |
|-----------|------------------------|------------------------|-----------------------------|-------------------------------|
| Quran learning circle for teens | `learning_management` | Disabled by default; guardian may enable peer social overlay later | Tiered mastery (letters → words → short surahs → longer surahs) | "A quiet room where teens learn and practise recitation, with guardians able to see progress." |
| Teen study circle (peer collaboration) | `social_learning` | Enabled from day one | Light progression (topics or weeks, not strict stages) | "A focused space where teens study together, ask questions, and share notes." |
| Emotional support circle | `peer_support` | Enabled from day one | No ordered stages — cyclical reflection and support | "A gentle circle where members can share what they are carrying and feel less alone." |

These defaults inform Genesis' initial mapping and Sage/Clio's expectations, but they are **advisory**: Observer's Dimensions 8–9 and Evolution Governor proposals can revise social layer, success dimensions, or progression when evidence shows a different shape serves the room better.

#### Learning Management: Service-First, Social Optional

**Applies to:** `ecosystem_type: learning_management` (e.g., education, skills training, certification prep)

For `ecosystem_type: learning_management`:

**Default surface hierarchy:**
1. **Minor / Learner surface** — primary learning interface (cards, visual tools, adaptive challenges)
2. **Guardian / Support dashboard** — progress view, scaffolding suggestions, struggle alerts
3. **Social overlay** (disabled by default) — guardian Teaching Circle, peer tips, discussion — only if guardian explicitly elects

**Default success dimension priority:**
1. Minor outcome dimensions (mastery, fluency, transfer) — highest weight
2. Minor experience dimensions (engagement, confidence, joy) — medium weight
3. Guardian quality dimensions (guardian scaffolding, coaching quality) — lower weight
4. Community health dimensions (peer support, discussion quality) — **weight 0.0** unless social layer is enabled

**When guardian enables social layer:**
- Community health dimensions become active with low initial weight
- Observer evaluates whether social interaction actually improves learning outcomes
- If peer support does not improve outcomes, Observer recommends disabling social layer
- Guardian Admin retains veto

**Why this matters:** A learning cluster is not "a social network with flashcards." It is a curriculum delivery system where the minor is the primary user. The guardian is the steward. Social features may help the minor learn from peers, but they must earn their place through evidence.

### 1.4 Creator Type and Ecosystem Scope

Every cluster records `creator_type` at creation. This determines ecosystem capabilities, not quality.

| Capability | `platform_admin` | `user` |
|------------|------------------|--------|
| Genesis adaptive probing | Yes | Yes |
| Cluster vault | Yes (pre-seeded, 500 MB, 500 items) | Yes (empty, 100 MB, 50 items) |
| Subclusters | Yes | ❌ No |
| Cluster spawning | Yes | ❌ No |
| Cross-cluster links | Yes | ❌ No |
| Evolution Governor | Yes | ❌ No |
| Token budget | Elevated (104K) default | Standard (52K) default |
| Ecosystem scope | Network (parent + children) | Standalone only |

**Internal platform limits (not user-facing):**
- `user` clusters: soft limit of 50 members (enforced at platform level, not advertised externally)
- `platform_admin` clusters: no hard limit
- These limits prevent abuse; they do not define the cluster's value or quality

**Implications for ecosystem design:**
- `platform_admin` clusters can have hierarchical success models (parent cluster health aggregates child clusters)
- `user` clusters have flat success models (single cluster only)
- Observer anomaly detection for `user` clusters focuses on standalone dimensions only
- Spawn signals in `user` clusters are routed to platform admin as proposals (not automatic subcluster creation)

### 1.5 Service Mode and Social Layer Defaults

Every cluster records `service_mode` at Genesis. This determines the default social layer and UI surfaces.

| Service Mode | Description | Social Layer Default | UI Default | Can Convert |
|--------------|-------------|----------------------|------------|-------------|
| `individual` | Single minor + guardian (e.g., one teen + parent) | Disabled | Dashboard | Yes → `group` via guardian invite |
| `group` | Multiple minors (e.g., class, cohort, batch) | Enabled | Timeline | No (already group) |
| `hybrid` | Starts individual, guardian can invite others later | Disabled until guardian opts in | Dashboard → Timeline on conversion | Yes → `group` via guardian invite |

**Implications:**
- `individual` clusters prioritize minor outcome over community interaction
- `group` clusters prioritize peer support, shared experience, and collective learning
- Guardian can override social layer default at any time; this is a default, not a restriction
- `service_mode` is inferred by Genesis from guardian description (probe: "Is this just for your minor, or do you want others to join?")

### 1.6 Stakeholder Relationship Model (NEW)

The ecosystem does not just track *who* the stakeholders are — it tracks **what they want, how they relate, and how those relationships should evolve**.

**Per-stakeholder fields (in `cluster_genesis_spec.stakeholders`):**

| Field | Description | Example (Guardian) | Example (Minor) |
|-------|-------------|---------------------|---------------------|
| `intended_goals` | What this stakeholder wants from the cluster | "See minor succeed conceptually" | "Enjoy learning through engaging methods" |
| `relationship_dynamic.current_state` | Current emotional/behavioral pattern | "Anxious micromanager" | "Resistant learner" |
| `relationship_dynamic.power_balance` | Who dominates the interaction | "Guardian dominant" | "Minor avoids" |
| `relationship_dynamic.conflict_pattern` | Recurring negative interaction cycle | "Pushes method → resists → both frustrated" | — |
| `relationship_dynamic.observed_signals` | CIM signals to watch for | "Over-explains", "Completes task for minor" | "Hides struggle", "Gives up after one mistake" |
| `transition_expectations` | Targeted evolution over time | Week 1-2: learn recommended methods; Week 3-4: shift to facilitating; Week 5+: confident independent exploration | Week 1-2: engage with interactive methods; Week 3-4: explain why; Week 5+: initiates practice in daily life |
| `interaction_patterns.warning_signals` | Behaviors that trigger Sage intervention | "Asks leading questions", "Does task for minor" | "Says 'I can't'", "Asks for answer without trying" |
| `interaction_patterns.positive_signals` | Behaviors that confirm progress | "Asks 'What do you see?'", "Minor volunteers explanation" | "Demonstrates without prompting", "Explains to guardian" |

**Why this matters:**
- Sage uses `intended_goals` to align responses with stakeholder motivation (not just their role)
- Observer uses `relationship_dynamic` to detect when actual behavior deviates from expected (e.g., guardian still micromanaging at Week 6)
- Transition expectations set measurable behavioral targets for the ecosystem
- Interaction patterns give Sage specific, actionable coaching cues

**Domain-agnostic application:**
- Guardian-minor: guardian (wants minor to grow) + minor (wants guidance without judgment)
- Authorized adult-minor: teacher (wants minor to succeed) + minor (wants engaging methods)

The same relationship model applies — only the roles and goals change.

### 1.7 Ecosystem Intake Lens (Cluster-agnostic)

Genesis and the Intake Interpreter treat every incoming cluster idea as a **prospective ecosystem**, not just a set of tags. Before any domain-specific archetype is applied, they infer a small, cluster-agnostic set of dimensions — the **ecosystem intake lens**. This lens is what later shapes both `cluster_genesis_spec` and `cluster_ecosystem_spec`.

At minimum, the intake lens captures:

- **Failure & gap** — what keeps going wrong in the current tools or groups the founder is using (for example, "content gets lost in scroll", "conversations never go beyond surface depth").
- **Primary outcome** — what changes in the member's life if the cluster works (for example, "feel known", "keep documents findable", "have a place to process faith struggles").
- **Primary beneficiaries & stakeholders** — who the room is really for, and who else is involved or affected (beneficiaries, supporters, scholars, institutions) — later mapped into `stakeholders[]` (§1.6).
- **Interaction mode** — what members are actually doing together when the cluster works (depth conversation, topics + documents, coordination, broadcast, mixed).
- **Temporal shape & persistence** — whether value is in live moments, persistent artefacts, or both (for example, ongoing circle vs document archive vs time-bounded cohort).
- **Social layer shape** — how exposed participation is (solo, dyad, small group, large room) and any anonymity, gender, or privacy constraints.
- **Tool & capability needs** — whether the room obviously needs shared capabilities such as topic threads, private tips, vault-backed references, matching, or others from the platform tools registry.
- **Risk & guardrails** — what kinds of harm are most likely if the cluster goes wrong (for example, bad advice, harassment, burnout, theological overreach) — later informing Observer welfare profiles and Platform Rules checks.
- **Cadence & arc hints** — whether the room is a drop-in space, a weekly rhythm, or a long arc — later informing any ordered or unordered `progression_model`.
- **Non-negotiables** — what the cluster must *never* become (for example, a dating app, a fatwa hotline, a noisy chat group) — later enforced via success dimensions, tools, and Observer stewardship.

These intake dimensions **do not add new tables**. They are a conceptual normalization step between raw signals (waitlist forms, Scout reports, Clio inference) and the concrete specs that already exist:

- `cluster_genesis_spec` — composition, stakeholders, tools, vibe, soul manifestation profile, and related fields (see `CLUSTER_GENESIS_ENGINE.md` §3.3).
- `cluster_ecosystem_spec` — success model, progression model (if any), tool requirements, introspection targets (§2–§5 of this document).

The intake lens keeps Genesis prompts **stable and cluster-agnostic** even as new archetypes, tools, and domains are added. Archetypes remain advisory overlays on top of this lens, not replacements for it. This keeps the architecture descriptive rather than prescriptive: new cluster shapes can still emerge, as long as they can be described in terms of failure, outcome, stakeholders, interaction, time-shape, and risk.

## 2. Multi-Dimensional Success Model

The ecosystem defines success as a **weighted set of dimensions** that Genesis infers from founder intent and Observer reweights based on evidence.

> ⚠️ **Phase 1 (v1):** Success model is **static** — generated by Genesis, editable by admin via dashboard. Observer flags when metrics look wrong. Admin manually adjusts. No auto-proposals, no member polls.  
> ⚠️ **v2 Deferred:** Observer auto-proposes changes. Governor routes.  
> ⚠️ **v3 Deferred:** Member deliberation via Clio polls.

### 2.1 Success Model Schema (Abstract)

> For a concrete, domain-specific example of a success model, see `architecture/examples/cluster-spec-parents-teaching-fractions.md` §6.1.

```json
{
  "version": 1,
  "last_reviewed": "[ISO date]",
  "review_schedule_days": 30,
  "dimensions": [
    {
      "id": "[dimension_id]",
      "name": "[Human-readable dimension name]",
      "description": "[What this dimension measures and how]",
      "weight": 0.40,
      "confidence": 0.90,
      "source": "founder_intent | latent_inference | behavior_signal | emergent_need",
      "rationale": "[Why Genesis assigned this weight and source]",
      "measurement": "cim.[subsystem].[metric_name]",
      "status": "active | deprecated | proposed",
      "floor_weight": 0.20
    }
  ]
}
```

**Field definitions:**
- `id`: Machine-readable identifier (e.g., `conceptual_understanding`, `guardian_confidence`, `minor_engagement`)
- `name`: Human-readable label displayed in admin dashboard
- `description`: What this dimension measures and how it is evaluated
- `weight`: 0.0–1.0 relative importance. Sum of all weights = 1.0
- `confidence`: Genesis certainty in this weight assignment
- `source`: How this dimension was discovered (see §2.2)
- `rationale`: Why Genesis assigned this weight and source
- `measurement`: CIM subsystem and metric that tracks this dimension
- `status`: `active` (live), `deprecated` (no longer tracked), `proposed` (pending admin approval)
- `floor_weight`: Minimum weight this dimension can hold without admin override

### 2.2 Dimension Source Classification

| Source | Description | Confidence Range | Example |
|--------|-------------|-----------------|---------|
| `guardian_intent` | Explicitly stated in guardian description | 0.80–0.95 | "I want my minor to understand the core concept" |
| `latent_inference` | Inferred by Genesis from language patterns, but not explicitly stated | 0.50–0.75 | Guardian says "I feel lost" → self-efficacy is a latent need |
| `behavior_signal` | Detected from actual user behavior post-launch | 0.40–0.65 | Guardians reply 4× more to frustration posts than resource posts |
| `emergent_need` | Discovered when users use the cluster in unexpected ways | 0.30–0.55 | Guardians start sharing related-topic anxiety — cluster scope broadens unexpectedly |

### 2.3 Floor Weight Rule

Every dimension has a `floor_weight` — the minimum weight it can hold without explicit admin override.

- **Guardian-intent dimensions** must have `floor_weight ≥ 0.20` — prevents the cluster from drifting away from its guardian's purpose
- **Latent-inference dimensions** should have `floor_weight ≥ 0.05`
- **Behavior-signal / emergent dimensions** can have `floor_weight = 0.00` — they are experimental and can be deprecated

**Why:** Prevents Observer from accidentally deprecating the cluster's core purpose.

### 2.4 Dimension Lifecycle

```
proposed → discussed → active → under_review → deprecated → archived
```

| State | Meaning | Who Can Set |
|-------|---------|-------------|
| `proposed` | Suggested by Genesis or Observer, not yet approved | Genesis, Observer |
| `discussed` | Admin (or v3: member poll) has deliberated | Admin, Governor |
| `active` | Weighted into ecosystem health score | Admin, Governor |
| `under_review` | Evidence suggests weight should change or dimension should be split/merged | Observer |
| `deprecated` | No longer relevant, but kept in history | Admin, Governor |
| `archived` | Removed from active model, preserved for analysis | Admin only |

### 2.5 Ecosystem Health Score

Single scalar derived from weighted dimension performance:

```
health_score = Σ (dimension_weight × dimension_performance)

where dimension_performance = normalized_score [0,1] from CIM measurement
```

**Not for gamification.** Not shown to users. Used by:
- Observer to trigger evolution proposals
- Governor to prioritize budget allocation
- Admin dashboard to see "is this cluster fulfilling its purpose?"

## 6. Observer: Success Skeptic (v1)

> ⚠️ **Phase 1 (v1):** Observer evaluates ecosystem health and **flags anomalies** to admin. It does **not** auto-propose success model changes. Admin reviews flagged anomalies and decides.  
> ⚠️ **v2 Deferred:** Observer auto-proposes changes with structured rationale.  
> ⚠️ **v3 Deferred:** Member deliberation on high-stakes changes.

### 6.1 v1 Observer Responsibilities

| Task | Frequency | Output |
|------|-----------|--------|
| **Health score computation** | Weekly | `ecosystem_health_report` JSON |
| **Anomaly flagging** | Weekly | `ecosystem_anomaly_flags` array |
| **Dimension drift detection** | Bi-weekly | `dimension_drift_alert` if guardian-intent dimension drops below floor |
| **Latent need detection** | Monthly | `latent_need_signal` (low-confidence, informational only) |

### 6.2 Anomaly Types (v1)

| Anomaly | Example | Admin Action |
|---------|---------|--------------|
| **Dimension underperformance** | `[core_dimension_id]` performance = 0.25 for 14 days | Review: Is the primary tool working? Is the stage too hard? |
| **Dimension conflict** | `[dimension_a]` and `[dimension_b]` inversely correlated (r = -0.68) | Review: Should one dimension be deprioritized? |
| **Guardian-intent drift** | `[core_dimension_id]` weight dropped from 0.40 to 0.15 (below floor 0.20) | **Urgent:** Cluster is losing its purpose. Admin must intervene. |
| **Emergent need signal** | Guardians posting about related-topic anxiety | Review: Is this a latent need to capture, or a signal for cluster spawn? |

## 7. Deliberation Mechanism

> ⚠️ **Phase 1 (v1):** All success model changes are **admin-initiated** via dashboard. Observer provides anomaly reports as input. No auto-proposals, no member polls.  
> ⚠️ **v2 Deferred:** Governor routing table.  
> ⚠️ **v3 Deferred:** Clio-facilitated member polls.

### 7.1 v1: Admin-Driven Changes

Admin edits success model via dashboard panel:
- Add/remove dimensions
- Adjust weights (with floor enforcement)
- Change measurement mappings
- Mark dimensions as deprecated

**Required fields for any change:**
- `change_rationale` (free text — why this change?)
- `expected_impact` (which dimensions/stages will this affect?)
- `review_date` (when to evaluate if the change worked)

**All changes logged in `revision_history`.**

### 7.2 v2 (Deferred): Governor Routing

When Observer auto-proposes changes, Governor routes by risk:

| Proposal Type | Route | Deliberation |
|--------------|-------|-------------|
| Weight change ≤ 10% | Auto-approve | None |
| Weight change > 10% or new dimension | Admin notification + 48h window | Admin reviews, approves, or requests Clio member poll |
| Dimension deprecation | Admin notification + Clio-facilitated discussion | Member input via lightweight poll |
| Latent need alert (high confidence) | Immediate Sage post + Admin notification | Admin decides whether to add as new dimension |
| Founder-intent drift | **Urgent admin review** — never auto-approve | Human decision required |

### 7.3 v3 (Deferred): Clio-Facilitated Poll

For member-facing decisions:
- Clio asks one question in-cluster
- Anonymous emoji response: 👍 / 🤷 / 👎
- Results feed into Governor decision, not binding
- Never poll same user >1/month on model changes

## 8. Activity History & Inference

All cluster-level and member-level activities are logged with server-generated timestamps for longitudinal understanding, agent context, and platform improvement.

### 8.1 Tables

| Table | Purpose | Key Fields |
|-------|---------|------------|
| `cluster_activity_log` | Cluster-wide events | event_type, event_data, actor_type, actor_id, inference_result, **timestamp** |
| `member_activity_log` | Per-member events | member_id, event_type, event_data, cim_signal, inference_result, **timestamp** |
| `cluster_fit_decision` | Genesis fit assessment | founder_id, searched_dimensions, matches_found, decision, timestamp |

**Timestamp requirements:**
- Server-generated (not client-submitted) to prevent clock skew
- Millisecond precision, ISO8601 with timezone
- Supports time-series queries: range scans, `ORDER BY timestamp DESC`
- Used by Sage for chronological member context
- Used by Observer for drift detection over time

### 8.2 Event Types

**Cluster-level:** genesis_probe, spec_change, feature_spawn, vault_add, vault_alignment, spawn_proposal, admin_decision, phase_transition, budget_change, member_joined, member_left

**Member-level:** tool_use, stage_complete, agent_interaction, sentiment_signal, error_pattern, help_request, vault_reference, progress_milestone

### 8.3 Inference Pipeline

1. **Raw events** → stored immediately in activity logs
2. **Weekly aggregation** → LLM summarizes patterns (e.g., "Beneficiary prefers visual model over abstract model"; "Supporter shifted from asking for answers to asking guiding questions")
3. **Stored inference** → saved back to `inference_result` JSONB
4. **Consumption** → Sage uses for member context; Observer uses for drift detection; Genesis uses for future cluster improvements

### 8.4 Access Control

| Role | Access |
|------|--------|
| Agent (Sage, Scout) | Query member activity for context (last N events, time range) |
| Agent (Observer) | Query cluster activity for drift detection |
| Founder | Dashboard view: anonymized member trends, cluster activity summary |
| Admin | Full logs for platform improvement and audit |
| Member | Own activity only (via personal dashboard) |

## 11. Ecosystem Adoption Phases (Seed / Sprout / Canopy)

Ecosystems mature with the cluster. Phase transitions are **automatic** based on telemetry, not manual project gates.

| Phase | Trigger Conditions | What the Ecosystem Does | Observer Role | Admin Role |
|-------|-------------------|------------------------|---------------|------------|
| **Seed** | `member_count < 50` AND `cluster_age_days < 30` AND `ecosystem_status = active` | Static success model. Genesis-generated. Admin-editable only. No auto-changes. | Measure + flag anomalies only. No proposals. | Review Genesis output. Edit weights. Approve or reject initial model. |
| **Sprout** | `member_count ≥ 50` AND `cluster_age_days ≥ 30` AND `first_behavior_signal_detected = true` | Observer auto-proposes changes. Governor routes (auto-approve ≤10%, admin review >10%). Admin batch review digest weekly. | Propose + measure + validate. Back-and-forth with ecosystem. | Batch-review proposals. Override auto-approves if needed. |
| **Canopy** | `member_count ≥ 200` AND `cluster_age_days ≥ 90` AND `success_model_revisions ≥ 2` | Member deliberation via Clio polls on high-stakes changes. Observer self-introspection (accuracy scoring). Purpose drift auto-detection with spawn recommendation. | Full skeptic mode. Challenge own accuracy. Question whether success model is still right. | Final veto on all changes. Decide on spawn vs sub-surface when drift detected. |

### Reverse transitions

| From | To | Trigger |
|------|-----|---------|
| Canopy | Sprout | `member_count < 150` for 60 consecutive days |
| Sprout | Seed | `member_count < 30` for 30 consecutive days |

**Why reverse:** A shrinking cluster loses the signal density needed for complex deliberation. Reverting to a simpler phase prevents false positives from thin data.

### Initial admin review gate

Before any phase begins, the ecosystem spec must pass **initial admin review**:

```json
{
  "ecosystem_status": "pending_admin_review",
  "review_checklist": {
    "dimensions_match_founder_intent": false,
    "floor_weights_protect_core_purpose": false,
    "progression_model_appropriate": false,
    "tool_requirements_achievable": false,
    "introspection_targets_measurable": false
  }
}
```

After admin approval: `ecosystem_status` → `active`, `ecosystem_phase` → `Seed`, CIMs begin measurement, Observer begins evaluation.

### Observer back-and-forth loop

```
Ecosystem declares: "Watch conceptual_understanding (weight 0.40, threshold 0.40)"
      ↓
Observer measures: "conceptual_understanding performance = 0.25 for 14 days"
      ↓
Observer flags: "Dimension underperformance — stage 3 scaffold needed"
      ↓
Admin reviews flag → edits ecosystem (adds visual_hint tool, splits stage 3)
      ↓
Ecosystem updates: "Now watch conceptual_understanding (weight 0.40, threshold 0.35, new tool)"
      ↓
Observer remeasures → loop continues
```

This loop is the core of ecosystem evolution. Ecosystem informs Observer what matters; Observer informs ecosystem when it's off track.

### CIM Measurement Implementation (Cluster-Type-Specific)

CIM measurements for ecosystem dimensions are **cluster-type-specific** and cannot be fully generic. The architecture provides the measurement key schema; implementation is delegated to type-specific modules:

| Ecosystem Type | Measurement Keys | Implementation Location |
|---------------|-----------------|--------------------------|
| `learning_management` | `cim.learner_state.mastery_depth`, `cim.engagement.child_voluntary_return_rate` | **Deferred to learning-domain CIM module** |
| `emotional_support` | `cim.sentiment.expression_depth`, `cim.network.peer_validation_density` | **Deferred to support-domain CIM module** |
| `career_reintegration` | `cim.career.network_growth`, `cim.career.opportunity_conversion` | **Deferred to career-domain CIM module** |

**Why deferred:** Each measurement requires domain-specific logic (e.g., "mastery depth" for fractions is different from "mastery depth" for Quran recitation). The ecosystem architecture defines the interface; domain teams implement the logic.

### Observer Self-Introspection (Canopy Phase Only)

When a cluster reaches **Canopy phase**, Observer evaluates its own accuracy:

1. **Outcome tracking:** For every Observer proposal that changed the ecosystem, track the actual outcome after 30 days.
2. **Accuracy scoring:** Compute `observer_accuracy = proposals_with_expected_outcome / total_proposals`.
3. **Calibration drift:** If accuracy drops below 0.60 for 3 consecutive proposals, flag `observer_calibration_drift` to admin.
4. **Self-correction:** Observer reduces confidence on future proposals by 0.10 until accuracy recovers.

**Why Canopy-only:** Seed and Sprout phases don't have enough proposal history to meaningfully score accuracy. Canopy clusters have ≥2 revisions and ≥90 days of data.

**Implementation:** Add to `OBSERVER_SYSTEM_PROMPT.md` when Canopy-phase behavior is wired. Add `observer_accuracy_logs` table to track proposal → outcome mapping.
