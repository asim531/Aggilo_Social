Goal
- Define and adopt `ClusterRequirement` as the canonical envelope for all cluster-intent signals (generic, premium, Scout, Observer, admin) before Genesis inference.

Scope
- Architecture:
  - `CLUSTER_GENESIS_ENGINE.md` – §2.0 `ClusterRequirement` is the source of truth.
  - `AGENT_COMMUNICATION_CONTRACT.md` – Pattern 7 / Cluster Intake Pipeline reference it by name.
- Runtime:
  - All intake code paths construct a `ClusterRequirement` struct from their raw signals and pass it to Genesis as part of the prompt input.

Requirements
- Document `ClusterRequirement` clearly in `CLUSTER_GENESIS_ENGINE.md` (already added) and ensure references in:
  - `AGENT_COMMUNICATION_CONTRACT.md` Pattern 7 summary
  - Any intake-related PRDs that discuss cluster creation.
- Implement a backend `ClusterRequirement` type/DTO mirroring the architecture contract.
- Implement mappers from:
  - Waitlist submission → ClusterRequirement
  - Premium application → ClusterRequirement
  - Scout intake signal → ClusterRequirement
  - Observer spawn proposal → ClusterRequirement
  - Admin seed input → ClusterRequirement
- Ensure Genesis calls use `ClusterRequirement` + source-specific extras rather than raw forms.

Acceptance Criteria
- For any new cluster created in Phase 1, devs can show the `ClusterRequirement` object that preceded its `cluster_genesis_spec`.
- Pattern 7 docs and Genesis docs use the same field names and meanings for `ClusterRequirement`.
- Code search shows a single mapping layer where all intake sources are normalised into `ClusterRequirement` before Genesis.
