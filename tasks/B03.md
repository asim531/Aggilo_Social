Goal
- Create Activity events table and aggregation endpoint for Activity tab (6.1).

Scope
- DB schema + backend service + API endpoint.

Requirements
- Schema fields: id, user_id, type (cluster_activity|clio_match|member_joined|timeline_update|dm_request|other), title, body, cluster_id nullable, thread_id nullable, created_at, read_at nullable, dismissed_at nullable.
- Sources: posts (new), clio matches, member joins, DM requests; allow extension.
- API: GET /api/activity returns grouped by date (Today/Yesterday/This Week) sorted desc; supports pagination.
- Stage gating: only for Stage 2+ (exclude otherwise).
- Mark read/dismiss endpoints optional (if time) or include read_at on fetch when opened.

Dependencies
- Auth middleware; source events from posts/DM/Clio signals.

Plan
- Add migration for activity_events table with indexes on user_id+created_at.
- Implement aggregation service that inserts rows on source events (hooks/stubs).
- Implement GET /api/activity with grouping and pagination.
- Add tests for insertion and retrieval grouping.

Files to Touch
- `supabase/migrations/*` (or migration folder)
- `apps/api/src/routes/activity/*.ts`
- `apps/api/src/services/activity.ts`
- Tests under `apps/api/test/activity.test.ts`

Validation
- Create sample events; GET returns grouped sections; Stage 1 user returns 403/empty.

Risks & Mitigations
- Risk: event fan-out complexity. Start with synchronous inserts; move to async jobs later.
- Risk: pagination grouping. Use server-side grouping by date buckets.

Out of Scope
- Push notifications (handled B04/B12); UI.
