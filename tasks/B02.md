Goal
- Build DM APIs to support request→accept→message flow with single thread per user-pair across clusters.

Scope
- Fastify routes + handlers + tests; minimal frontend stubs if needed for e2e.

Requirements
- Endpoints:
  - POST /api/dm/request (cluster_id, recipient_id, intro_text) → creates dm_request + thread (if none).
  - POST /api/dm/respond (request_id, action=accept|decline) → updates status; accept links to thread.
  - GET /api/dm/conversations → lists threads with last message, unread counts.
  - POST /api/dm/send (thread_id, body) → inserts message if participants and accepted.
- Business rules:
  - One thread per user-pair; new request reuses existing thread (pending or accepted) across clusters.
  - Pending requests expire in 30 days; decline is silent to sender (status pending for 30 days in sender view).
  - Stage gating: only Stage 3 users can send requests.
- RLS: participants-only access to their threads/messages.
- Tests: request→accept→message; duplicate request merges; unauthorized access blocked.

Dependencies
- DM schemas (B01); auth middleware; stage gating flag.

Plan
- Implement service layer for thread lookup/creation (pair-unique).
- Add Fastify routes with validation and RLS checks.
- Add expiry/decline handling.
- Write integration tests for flows and cross-cluster merge.

Files to Touch
- `apps/api/src/routes/dm/*.ts`
- `apps/api/src/services/dm.ts`
- Tests under `apps/api/test/dm.test.ts`

Validation
- `pnpm test dm` (or equivalent) passes.
- Manual: create two users, send request, accept, message, attempt duplicate request from other cluster → same thread.

Risks & Mitigations
- Risk: race on thread creation. Use transaction with pair-unique constraint.
- Risk: privacy leak via list. Ensure list is participant-scoped via RLS and query filters.

Out of Scope
- UI rendering; realtime subscriptions (handled later).
