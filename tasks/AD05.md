Goal
- Provide clear admin dashboards for the cluster intake pipeline (Pattern 7) and Genesis Re-Eval outcomes (CLUSTER_GENESIS_ENGINE §10).

Scope
- Admin-facing React screens/components only.
- No schema changes; consumes existing tables (`cluster_intake_signals`, `cluster_intake_drafts`, `genesis_re_eval_log`, etc.).

Requirements

1. Cluster Intake Queue
- List view:
  - Table of `cluster_intake_signals` with: id, signal_source, created_at, status, and a short summary (e.g. inferred title/who/purpose).
  - Filters by source (waitlist, Scout, Clio), status, and created_at window.
- Detail view for a single intake signal:
  - Show a **human-readable summary first**: who the room is for, what it is for, and any key reviewer concerns.
  - Provide a "Show technical details" toggle that reveals the raw structures: Draft v1 spec (AGGIL config, cluster name, description, Sage persona, Clio onboarding, seed questions, Atlas brief, Scout brief, interpretive assumptions), adversarial critique JSON rendered as a list of challenges/confirmations, Draft v2 spec, structured v1→v2 diff, and held positions.
  - Admin actions:
    - **Approve as-is** → calls backend to mark v2 (or v3) as approved and fire `ClusterCreationJob`.
    - **Edit and approve** → opens inline edit form for key fields (name, description, AGGIL config, persona notes), saves as v3, then approve.
    - **Reject** → prompt for rejection_reason, send to backend, archive record.
- UX constraints:
  - Clearly label Source A (human-submit) vs Source B/C (Scout/Clio) to avoid sending rejection emails where none are needed.
  - Avoid protocol disclosure in copy; talk about "your cluster idea" and "how we understood it", not internal pattern numbers or job names.

2. Genesis Re-Eval Dashboard
- List view:
  - Table of `genesis_re_eval_log` (or equivalent) with: cluster_id, cluster name, trigger_type, trigger_reason, created_at, recommended_action, disruption_level.
  - Filters by trigger_type (`scheduled_quarterly` / `emergency_threshold`), recommended_action, disruption_level.
- Detail view:
  - Show a short narrative summary: what kind of room this is today, what Genesis thinks it is starting to behave like, and whether that suggests staying as-is, a small adjustment, a larger framework change, or spawning a sibling room.
  - Below the summary, show the technical details: current vs proposed ecosystem_type, dimensional_mismatches (dimension, current_weight, proposed_weight, evidence), and adverse_impact_estimate (affected_member_count, disruption_level).
  - Show recommended_action (`no_change`, `soft_pivot`, `hard_pivot`, `spawn_recommended`) and provide links to:
    - Related `evolution_proposals` (if any created from this Re-Eval).
    - Related `cluster_spawn_proposals` (if `spawn_recommended`).
  - Admin actions:
    - For `no_change`: no action, just archive/log.
    - For `soft_pivot`/`hard_pivot`: deep link into Evolution Governor UI (if exists) or a simple "open in Evolution view" button.
    - For `spawn_recommended`: deep link into Spawn Engine/admin screen.
- UX constraints:
  - Copy must not expose low-level mechanics (token budgets, decision trees); speak in terms of "framework fit" and "how the cluster is used", not "model confidence" or implementation details.

Validation
- Manual:
  - As a platform admin, open the Cluster Intake Queue, inspect at least one Source A and one Source B/C record, approve one, reject one.
  - As a platform admin, open Genesis Re-Eval list, inspect at least one entry, verify current vs proposed ecosystem_type and dimensional mismatches display correctly.
- QA03:
  - E2E tests reference these dashboards when validating the intake pipeline and Re-Eval behaviour.

Risks & Mitigations
- Risk: exposing too much internal detail to admins makes UI noisy.
  - Mitigation: keep JSON raw views behind a "Show raw JSON" toggle; default to human-readable summaries.
- Risk: mis-click on approve/reject.
  - Mitigation: confirmation dialogs + clear labels, especially for irreversible actions.

Out of Scope
- Changing intake JSON shapes or adding new tables.
- Modifying Genesis or Evolution algorithms.
- Implementing new admin roles or permissions.
